# 县域农产品直播带货选品质检发货售后平台

以**商品批次**为主线的全链路平台：农户/合作社提交水果、米面、菌菇、蜂蜜、腊味等农产品 → 运营选品质检（样品试吃）→ 直播排期（上架前履约检查）→ 仓库锁库锁包材 → 直播下单自动生成分温区发货任务 → 售后工单 → 农户结算 → 县域运营复盘。售后结论反向回流到下一场的选品、主播口径、预售量与县域公共品牌公告。

## 技术栈

- **前端**：Vue 3 + Vite + Element Plus + Pinia + Vue Router + ECharts
- **后端**：NestJS 10 + TypeORM（JWT 认证 + 角色权限）
- **数据库**：PostgreSQL 15（首次启动自动建表并写入演示种子数据）

## 一键启动（Docker Compose）

```bash
docker compose up -d --build
```

| 服务 | 地址 |
|---|---|
| 前端（nginx） | http://localhost:8080 |
| 后端 API | http://localhost:3000/api |
| PostgreSQL | localhost:5432（postgres/postgres，库 agri_live） |

后端首次启动时自动同步表结构并写入种子数据（8 商品 / 9 批次 / 5 场直播 / 790 笔订单 / 23 张售后工单 / 风险事件与结算单），无需手动初始化。

## 本地开发

```bash
# 1. 数据库（任选其一）
docker run -d --name pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=agri_live -p 5432:5432 postgres:15-alpine
# 或使用本机已有 PostgreSQL，创建数据库 agri_live

# 2. 后端（默认连 localhost:5432，可用 DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_NAME 覆盖）
cd backend && npm install && npm run build && npm start   # http://localhost:3000

# 3. 前端（vite 已配置 /api 代理到 3000）
cd frontend && npm install && npm run dev                 # http://localhost:5173
```

## 核心页面与业务闭环

1. **商品与批次**（农户）：填写产地、采摘时间、规格、库存、检测报告及有效期、保质期、冷链温区、包装耐压、可供直播批次；运营在此审核商品。
2. **选品质检**（运营）：对待选批次做样品试吃评分（1-10）与质检决策，通过即 `qc_passed`。
3. **直播排期**（运营）：选批次时自动弹出**上架前履约检查**——样品口感、检测报告有效期、采摘窗口、保质期覆盖、包装耐压、冷链可达城市、农户交货稳定性、可供库存八项对照，给出建议预售上限；创建场次含主播、脚本、承诺口径、价格、优惠券、预计销量。
4. **库存锁定**（仓储）：按直播排期锁定库存与包材（县域中心仓/前置仓），可释放。
5. **直播执行**：开播 → 模拟下单（订单自动扣库存、超预估即触发 `oversell` 风险）→ 每单自动生成发货任务（订单+批次+发货仓+物流温区+随单承诺）。
6. **发货任务**（仓储）：发货/送达/异常；冷链任务可上报**冷链车晚到**，自动生成链路风险。
7. **售后工单**（售后）：坏果、少发、物流延误、地址错误、用户拒收、口味不符六类；坏果工单自动回算批次坏果率，超 5% 触发 `defect_rising` 风险；处理后发起**反向决策**（继续/暂停农户、调整主播口径、降低预售量、发布品牌风险说明——后者自动生成公告草稿）。
8. **农户结算**：直播结束后按 `供货价 × 销量 − 售后扣减` 生成结算单，运营打款。
9. **风险中心**：超预估、少供、报告过期、冷链晚到、坏果率升高、承诺不符六类事件的知晓/处置；支持一键扫描检测报告过期批次。
10. **批次链路**：任一批次的时间线视图，串起选品→直播→锁库→订单→发货→售后→结算→风险→反向决策。
11. **复盘分析**（运营）：农户稳定性评级（稳定/观察/谨慎）、品类适合直播指数、售后原因分布、**售后对复购率的影响**（有售后记录客户 vs 无售后客户复购率对比）。
12. **爆单分配**（运营/农户/售后）：直播销量爆单（超预估）后一键生成库存分配方案——仅**已质检批次**参与，**采摘早（成熟度高）的批次优先**，逐单校验**物流时效**（冷链可达城市 + 剩余保质期覆盖运输天数），同池内按**订单付款时间**先到先得；分不到的订单进入**延迟通知**，用户可选择**等待 / 换规格（同品类现货批次，差价平台补贴）/ 退款（原路 1-3 个工作日）**；库存缺口自动生成农户**追加采摘任务**（含成熟度/糖度/单果重等质量要求与截止时间），追加批次**独立建档、必须重新质检合格**后才自动补发等待中的订单，**不得混入已锁定批次发货**；方案生成时同步产出**客服分层话术**（延迟发货解释 / 规格替换说明 / 退款等待时间）。

- 批次 `B20260910-LA-01`：检测报告 2026-10-03 已过期（report_expired）+ 主播承诺「纯手工无添加」与实际配料不符（promise_mismatch）→ 已生成品牌风险公告与「暂停该农户排播」决策
- 批次 `B20260928-KW-01`：直播中，农户预警连续降雨将少供（undersupply）
- 直播「赣南脐橙爆甜专场」：预估 150、实售 360（**2.4 倍爆单**），320 笔订单待分配（含 8 笔冷藏冷链不可达城市订单）；主批次 `B20261002-OC-01` 已穿仓，备选批次 `B20261005-OC-02`（已质检 120 件）与礼盒批次 `B20261003-OC-G1`（换规格现货 60 盒）可用于演示完整爆单分配链路

## 爆单分配演示步骤（种子数据已内置爆单场次）

1. 运营 `ops/123456` 登录 → 菜单「爆单分配」→ 默认选中「赣南脐橙爆甜专场」（实 360/估 150），预检显示：待分配 320 单 / 需求 360 件 / 已质检可分配 270 件（本场锁定 150 + 备选批次 120）/ 冷链不可达 8 单。
2. 点击「生成分配方案」→ 按时发货 239 单（自动生成发货任务）、81 单进入延迟通知、缺口 82 件自动生成农户追加采摘任务，同时生成 3 条客服分层话术与 critical 级 oversell 风险事件。
3. 「延迟通知」页签逐单登记用户选择：**等待**（进入补发队列）/ **换规格**（仅列出同品类、已质检、有库存、物流可达批次，如脐橙礼盒）/ **退款**（订单即转已退款）。
4. 农户 `farmer1/123456` 登录 → 「爆单分配」看到追加采摘任务（82 件、质量要求、截止时间）→ 提交采摘 → 生成独立批次 `B…-EX…`（**pending 待质检，不参与分配**）。
5. 运营在「追加采摘」页签对该批次**复检**：合格 → 批次转 `qc_passed` 并自动补发选择「等待」的订单；不合格 → 批次 `qc_failed` + 风险事件，农户可重新提交。全部通知处理完后方案自动「已收官」。
6. 售后 `aftersales/123456` 登录可查看方案、登记用户选择、复制客服话术。

## 验证方式（本题实际执行过的验证）

在本地环境（Node 22 + PostgreSQL 15）实际执行并通过：

1. **构建**：`backend: tsc 编译通过`；`frontend: vite build 通过`。
2. **接口冒烟**：登录各角色账号；`GET /api/analytics/overview` 返回 8 商品/790 订单；履约检查接口对蜂蜜批次返回 8 项全 ok。
3. **爆单分配全链路**（curl 逐步执行，全部通过）：预检（320 单/需求 360 件/可分配 270 件/冷链不可达 8 单）→ 生成方案（2.4 倍爆单，按时 239 单、延迟 81 单、缺口 82 件、3 条话术、1 个采摘任务、oversell critical 风险）→ 分配明细按付款时间排序且来源批次为锁定库存+备选批次 → 延迟通知三种选择各自生效（等待/换礼盒批次/退款 ¥29.90）→ 农户提交追加采摘 82 件生成 `pending` 批次 → 运营复检合格 → 等待订单自动补发并生成发货任务 → 全部通知处理完方案转「已收官」。
4. **约束验证**：追加采摘批次在复检合格前为 `pending`，不在可分配批次状态（qc_passed/on_sale/locked）内，且独立建档不并入任何锁库记录；复检不合格路径产生 `qc_failed` 批次 + critical 风险事件，农户可重新提交；重复生成方案返回 409；农户/未登录访问受 403/401 拦截；冷链不可达城市的订单换规格选项为空、选择等待也不会被追加批次补发（物流时效约束贯穿始终）。
5. **异常注入**：农户临时少供（300→280）与坏果率上报 7%，风险中心实时出现 `undersupply`、`defect_rising` 事件。
6. **复购分析**：种子客户池 400 人，有售后记录客户复购率显著低于无售后客户（复盘页图表可读）。

> 说明：本工作区无 Docker 守护进程，Compose 配置按标准多阶段构建编写（backend: node20 构建+tsc 编译；frontend: node20 构建+nginx 托管并反代 /api），与本地验证通过的构建命令一致。
